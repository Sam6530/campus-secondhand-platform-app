# 校园二手交易与物品流转平台

## 3 成员分工

| 成员 | 主要职责 |
|---|---|
| A | 前端公共工程、用户交易页面、页面交互和前端自测 |
| B | 核心交易后端、数据库升级、事务并发、收藏评价、统计与通知 |
| C | 身份会话、认证审核、举报争议、聊天后端和管理页面 |
| D | 阶段验收、独立复核、缺陷复验、测试文档和证据整理 |

A、B、C分别完成所负责模块的实现与自测，D依据共同确定的需求、接口和验收标准进行阶段复核。接口或规则需要协调时，由相关成员共同确认后同步更新代码与文档。

V3阶段采用全组共同检查和修复的方式，不再按照A、B、C、D划分问题归属。成员共同发现问题、核对影响范围并完成回归，最终结果统一记录在V3复验材料中。

## 4 分支含义

| 分支 | 含义 |
|---|---|
| `main` | 当前正式主线，保存已经完成阶段复核的稳定版本 |
| `v1-a` | A在V1阶段完成的前端实现与自测材料 |
| `v1-b` | B在V1阶段完成的核心业务后端与数据实现 |
| `v1-c` | C在V1阶段完成的身份、治理与管理功能 |
| `v1-d` | D在V1阶段汇总A、B、C的实现，执行核心闭环、接口、权限和数据一致性复核后形成的验收确认版本 |
| `v2-a` | A在V2阶段完成的前端扩展内容 |
| `v2-b` | B在V2阶段完成的后端与数据扩展内容 |
| `v2-c` | C在V2阶段完成的身份治理与管理扩展内容 |
| `v2-d` | D在V2阶段执行完整业务、数据升级、可靠性及回归复核后形成的验收确认版本 |
| `v3` | 全组共同开展问题检查、修复与系统回归形成的版本 |

阶段内先由A、B、C提交各自负责的实现，再由D核对共同需求、接口契约、测试结果和证据材料。D不重复承担A、B、C的模块开发，而是从集成结果出发发现问题、组织复验并确认阶段是否达到进入下一阶段的条件。`v1-d`和`v2-d`分别保存对应阶段的验收结果；V3由全组共同处理问题，因此不再拆分成员分支。

## 5 Issue处理规则

Issue用于记录能够复现并需要跟踪的问题。一个Issue完成处理需同时满足以下条件：

1. 问题的触发条件、实际结果和预期结果明确。
2. 修复内容已经进入当前阶段目标分支。
3. 原问题场景复验通过，相关功能完成必要的回归检查。
4. 测试用例、复验结果或证据记录能够对应到该Issue。
5. 复核人员确认问题不再出现后，将Issue关闭。

V3的Issue由全组共同检查，处理结果汇总在[问题修复与复验记录](documents/testing/V3问题修复与复验记录.md)中。

## 6 使用方法

### 6.1 线上访问

在浏览器中打开[线上项目](http://47.118.56.222)，即可进行注册登录、物品浏览、发布、咨询、下单及其他业务操作。

### 6.2 本地运行

1. 安装JDK 17及以上版本、Node.js、Maven和MySQL，或使用Docker Desktop。
2. 根据[工程实现与启动说明](implementation/README.md)准备数据库连接和初始管理员配置。
3. 在`implementation/frontend/`中安装依赖并构建前端。
4. 使用`implementation/build.ps1`构建后端。
5. 使用`implementation/start.cmd`启动项目，使用`implementation/stop.cmd`停止项目。
6. 浏览器访问`http://127.0.0.1:18080`。

测试代码位置、运行命令和阶段结果见[系统测试记录](documents/testing/系统测试记录.md)，完整报告见[校园二手交易与物品流转平台系统测试报告](documents/testing/校园二手交易与物品流转平台系统测试报告.docx)。
