# 数据与状态设计

版本1.0，2026-11-12。本文件规定系统的核心数据对象、状态联动、事务边界、并发控制和数据维护职责。

## 1 数据结构与维护边界

| 数据对象 | 关键业务内容 | 约束与维护职责 |
|---|---|---|
| accounts | 账号标识、昵称、密码哈希、角色、认证及限制状态 | 账号名唯一；C维护身份与权限，公开接口使用字段投影 |
| verifications | 申请人、认证材料、申请状态、审核原因和时间 | 申请人与账号关联；C维护认证流程 |
| assets | 上传人、用途、存储引用、类型和大小 | 按关联对象授权访问；B、C按业务用途共同使用 |
| items、item_versions | 卖方、标题、分类、描述、价格、图片、版本及状态 | 物品版本唯一，历史版本保留；B维护内容，C执行审核和治理 |
| orders、reservations | 买卖双方、物品版本、交易快照、订单阶段和完成时间 | 单件物品至多一个有效占用；B维护交易与占用 |
| deliveries | 订单、登记人、说明、时间和版本 | 交付事实独立保存；B维护 |
| operation_receipts | 操作者、意图键、动作、请求摘要和结果引用 | 操作者与意图键唯一；B提供共享幂等机制 |
| favorites、reviews | 收藏关系、订单评价、评分、内容及展示状态 | 收藏关系唯一，交易双方各评价一次；B维护 |
| conversations、messages | 场景、业务对象、参与者、发送人、内容和时间 | 参与者由服务端确定，终态订单会话只读；C维护 |
| reports、disputes、dispute_evidence | 举报对象、理由、证据、状态、结论和关联事件 | 举报独立记录，争议证据追加保存；C维护 |
| audit_facts | 操作者、对象、动作、版本、前后态、理由和结果 | 关键业务与治理操作留痕；B、C共同使用 |
| notification_outbox | 收件人、事件键、内容、状态和尝试次数 | 事件键唯一，支持提交后投递和补投；B维护 |

B维护统一的数据库升级序列，C提供身份、治理和聊天的数据变化，A依据接口模型使用数据，D检查约束、升级和状态变化的可验证性。数据库结构通过新增升级脚本演进，并在`schema_migrations`中记录版本、说明、校验值和执行时间。

## 2 订单与物品状态

订单主流程为：

`待卖方确认 → 待交付 → 待买方确认 → 已完成`

卖方拒绝后进入已拒绝，普通取消后进入已取消，争议处置可以形成异常终止。订单状态转换由服务端依据角色、前态和业务事实执行。

| 事件 | 前态与角色 | 同一事务内的数据变化 | 一致性要求 |
|---|---|---|---|
| 新下单 | 买方资格有效；物品版本已审核且可交易 | 保存订单、快照、占用、回执、审计和通知事件 | 单件物品保持唯一有效占用 |
| 接受订单 | 卖方；待卖方确认 | 订单进入待交付，保存审计和通知事件 | 操作者与订单卖方一致 |
| 拒绝订单 | 卖方；待卖方确认 | 订单进入已拒绝，释放占用并计算物品状态 | 订单、占用和物品结果同步 |
| 交付登记 | 卖方；待交付 | 保存交付事实，订单进入待买方确认 | 交付记录与订单阶段同步 |
| 买方确认 | 买方；待买方确认且已有交付记录 | 订单完成、物品成交、释放占用并记录完成时间 | 重复请求返回同一业务结果 |
| 普通取消 | 交易当事人；满足取消边界 | 订单进入已取消，释放占用并重新计算物品状态 | 取消声明、交付事实和争议状态共同判断 |
| 争议受理与补证 | 未结束订单的当事人 | 保存争议及追加证据，保留原订单阶段和占用 | 证据按作者和时间顺序保存 |
| 争议终止 | 管理员依据证据处理 | 订单异常终止、释放占用并记录处置事实 | 订单不计入成交，物品进入相应治理状态 |
| 解除限制 | 管理员 | 只修改对应限制并重新计算可展示、可咨询和可交易条件 | 其他独立条件保持原状态 |

物品是否可交易由物品审核状态、隐藏状态、卖方资格、有效占用和治理状态共同决定。客户端提交业务动作，不直接指定任意目标状态。

## 3 事务、并发与幂等

共享对象按照“账户标识排序、物品、订单、争议或治理对象”的顺序加锁。服务在获得锁后重新读取状态并完成业务判断，相关数据变化在同一事务中提交。

重要写操作使用意图键。服务先核验操作者和业务对象，再查询操作回执：相同意图和相同内容返回已有结果；相同意图对应不同内容返回业务冲突；新的意图进入正常业务处理。

逻辑唯一检查与数据库唯一约束同时使用。锁竞争、唯一约束竞争和事务死锁采用明确的冲突响应；客户端使用原意图键重试，服务端重试时重新执行完整事务。

D通过MySQL多连接、同步屏障和数据库前后态断言验证并发行为。测试设施只在测试环境启用。

## 4 历史、隐私与文件

订单成立时保存物品描述、价格和版本快照，快照在订单生命周期内保持只读。举报、处置、争议证据和关键操作采用追加记录，形成可追溯的业务历史。

公开列表使用字段白名单，不返回认证材料、审核原因、联系方式和内部治理信息。本人接口提供与自身业务相关的完整记录，管理接口依据职责范围访问治理信息。隐藏物品的收藏记录使用不可用占位保留用户关系。

图片目录通过环境变量配置，业务响应使用资源标识而不是个人电脑绝对路径。资源接口根据上传人、业务用途和关联对象进行授权。图片类型、数量和容量由统一配置控制，服务端校验与前端提示保持一致。

## 5 通知与审计

业务事务同时保存必要审计事实和Outbox事件。事务提交后，通知服务按配置的批次和间隔处理待投递事件。事件键用于保持通知幂等，投递状态和尝试次数用于补投与运行检查。

审计记录包含操作者、业务对象、动作、版本、前后状态、理由、时间和结果。公开接口不返回审计内容，管理员在授权范围内查询。业务、通知和审计使用统一的对象标识及事件引用，便于阶段测试核对。
