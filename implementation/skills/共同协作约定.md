# 校园二手平台共同协作约定

## 输入与角色

沿用documents/requirements/需求规格说明书.md，按已有FR/UC/BR/ST核对，不重新写需求，不凭旧实现猜业务。先找原文明确结论，只有歧义、冲突或确需改动时才开Q，不能为每个已明确规则重复审批。当前需求的具体状态、优先级与既有参数优先于Skill示例；发现冲突先问，不暗改。

| 成员 | 实现责任 | 过程责任 |
|---|---|---|
| A | frontend公共基础、交易界面和前端集成 | 基线索引、阶段计划、任务依赖和全员验收组织 |
| B | backend交易、物品版本、订单占用、交付取消、持久化迁移和并发 | 架构/ADR/接口与关键设计统合 |
| C | 认证会话授权、审核、治理争议及对应管理页面 | 原需求规则核对、Q组织、测试预期业务澄清 |
| D | 沟通、通知、收藏、评价及信誉，对应页面接口 | 测试覆盖、缺陷与复验组织，系统测试文档汇总 |

每个人都是模块负责人。A不写完所有页面；C/D使用A的布局、客户端和公共组件实现自己的页面。D不是全组测试代工或云运维负责人，C不重写需求，B不包办所有后端。姓名由实际同学填写，不按字母猜GitHub账号。

## 代码边界与并行

V1开工准备共同约定frontend组件/路由及backend模块目录。C提供登录会话、鉴权和可复用对象授权能力，B/D在各业务服务落实具体对象/状态检查，不互相假定对方已全部校验。B维护共享ORM/SQL模型与迁移，C/D提供本模块schema和变更要求，共同评审后B统合，不建第二套表。

B/C/D分别写自己业务接口，提供方与A或对应调用方共同确认schema和错误；B只统合契约，不单方面决定。A先用同schema模拟数据，B/C/D先用合成数据及已确认共享接口并行，尽早真实联调。模拟不替代真实授权、MySQL或页面验收。

共享文件如入口、鉴权、数据库迁移、前端公共状态、依赖清单由负责人协调，避免并行覆盖。新增依赖说明理由和影响。当前技术路线参考旧Vue3/JavaScript/Vite、Java17/Spring Boot/MyBatis及MySQL，不把新客服项目的Python架构搬过来；具体基线由实际成员评审。

## 问题协商与文档滚动

有无法确定的内容，可以找其他负责的成员协商，输出问句就行。注明接收人、需求/接口、现状和选项、影响及阻塞范围；由同学转达，不自动向外发消息。不替其他成员作决定，未答复不算同意；当前版不依赖该结论的任务继续。

例：向B/C确认：争议结案与补证竞争时，原需求哪些条款决定可提交边界？锁后由谁重读、拒绝返回什么错误、D应怎样验证？

Q记录问题/依据/选项代价/决定/实际确认人角色日期/阻塞和影响/同步资产/复核。Q已有回答但文档未同步，只能“已决定待同步”；另一实际成员复核后关闭。技术取舍形成ADR，记录备选、理由、代价、验证、确认和重评条件，旧决定被替代时保留历史。普通缺陷无需硬凑ADR。

本轮流程：引用旧需求→Q澄清→相关ADR评审→同步架构基线→细化当前契约和关键设计→准备独立测试预期→任务准入→实现/审查/测试→阶段验收。不要等全部代码写完才补设计，或等V3才测试。修改同时更新涉及的设计/接口/用例/测试，正式决定不只留聊天。

## 人工责任与任务执行

AI先提出任务计划、范围、疑问和测试；实际成员核对并批准当前小任务。已有明确授权则在范围内继续，不反复确认。跨模块契约、需求变更、新依赖超出授权时先反馈，不能私改验收预期。

实际同学决定业务预期、ADR取舍、接口接受、任务准入和验收。作者检查关键逻辑，关键变更由另一成员审查，不能由AI替代。建议A↔B看页面/交易契约，C↔D看治理/沟通隐私；涉及权限、事务时按风险再找相关成员交叉检查，不以固定配对取代必要审查。

测试脚本和命令可由AI运行；须由实际成员核对预期与结果，再由审查人检查关键项。失败先判实现、测试或需求问题，改预期需依据和批准，不删断言追全绿。并发用真实MySQL多连接，内存/H2/单线程结果不冒充MySQL并发证据。

## 每版全员通过

只有V1、V2、V3三个版本。开工准备在V1内，不另加V0。前版未通过，下一版只可记录建议，不实施下一版功能。

每版确认同一代码和文档快照、完成范围及问题、正常链路和关键异常、模块检查与前版回归、设计同步及交叉审查。四名实际成员各自明确通过后，A汇总放行。沉默、单人代表全部、四个AI同意、测试全绿都不能代签。签后影响基线的变更要重新评估复核，旧签名不自动用于新快照。记录在documents/stages/阶段验收记录.md。
