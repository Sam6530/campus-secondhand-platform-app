# D 沟通反馈与验证组织

## 开始时读取

先读[共同协作约定](../共同协作约定.md)、[工程文档基线](../../../documents/README.md)、[阶段计划](../../../documents/stages/阶段计划.md)和[阶段验收记录](../../../documents/stages/阶段验收记录.md)。[原需求规格说明书](../../../documents/requirements/需求规格说明书.md)是已有输入：首次认识范围，做任务时按FR/UC/BR/ST定位原文，不重写需求、不凭代码反推规则。

首次初始化读[教师操作指引](../../../documents/references/架构设计后确认与分阶段实现操作指引.md)，按其中Q、ADR、接口、测试、任务、人工复核和验收要求执行。[记录模板](../../../documents/记录模板.md)提供字段；当前尚未形成的设计或任务先列缺项，不能当已确认。

当前V1准备，两版实现V1/V2，一版系统测试V3，没有另设V0。先输出本版范围、已有依据、计划/文件范围、依赖及测试，等实际同学批准对应任务；已授权任务在范围内继续，不反复确认。每版四位实际成员对同一基线全部通过才进下一版。AI只能建议，不能代签。

有无法确定的内容，可以找其他负责的成员协商，输出问句就行。说明接收人、需求/接口、冲突和选项、阻塞范围。受影响任务等结论，本版无关任务继续；不自动对外发消息或擅改共享协议。GitHub任何读写操作需本次用户明确确认，当前无远端授权。

## 每批交付

实现与文档同步，引用同一需求和快照；提供变更、契约影响、真实测试与回归、另一成员审查及后续问句。自己的测试自己准备和执行，AI可代跑但不能代替实际成员核对与验收。遇到失败先判实现/测试/需求，不删断言追全绿。旧代码复用注明来源，旧测试不算新轮结果；不自动启动服务器或云资源。

## 实现责任

主责物品咨询、订单会话、只读及会话参与者约束、站内通知、收藏、评价与信誉汇总，以及对应页面。使用A公共组件、C会话授权和B订单数据，数据库结构由B统合。D是实现成员兼验证组织者，不是原来只复核的D，也不负责替全组部署服务器。

遵循原需求的正常/异常及优先级；不擅自新增论坛等级、推荐算法、短信、支付或消息队列。真实需要新技术先与相关成员评审。

## 分阶段交付

| 版本 | 具体交付 | 关键检查 |
|---|---|---|
| V1 | 物品咨询、订单会话、参与者入口及基础站内通知，相关页面 | 不串他人会话，结束订单只读；通知失败行为符合原需求，不回滚已成立业务 |
| V2 | 收藏幂等、双方评价与信誉、公开隐私、通知持久重试及权限随状态联动 | 重试不反向取消收藏，不公开未审核/隐藏内容；原文与公开投影区别；通知重试不重复执行业务 |
| V3 | 聊天隔离/只读、公开隐私、收藏评价、通知故障及整链交叉验证 | 本轮真实证据、失败恢复与原反例复验；修D缺陷并提供系统测试供稿 |

## 兼任验证组织与追踪

各成员对自己的模块编写并执行测试，你维护覆盖索引和问题状态，不能把他们未跑的内容代填通过。测试预期先引用原需求、确认规则和独立业务走查，C组织歧义确认；AI和代码本身不能独自确定正确答案。

建立需求→Q/ADR/接口→Issue或本地任务→TC→修改版本→证据→复验关系。用原编号，不生成第二套重复需求。阶段功能全绿不替代四名实际成员对同一基线的验收，A负责组织放行，D提供证据覆盖和残余问题。

documents/testing中逐步维护测试用例、缺陷与复验、系统测试报告；编码前补独立预期，编码中跑模块检查，每次整合跑影响回归，每版走主流程和异常，V3集中做系统性测试。不要等V3才补测试，不生成虚构执行日期、数量或截图。

缺陷记录输入前态、预期依据/实际、影响和归属，交原负责人修复，另一成员复验。若测试错了，给依据与批准后才改测试；若需求矛盾则重开Q，不让验收标准追着代码变。真实MySQL竞争和浏览器观察分别登记，旧历史结果和本轮新执行分开。

## 必须维护和交接

交社区接口/页面、事务与通知衔接意见、模块测试和文档；与B确认业务提交/通知失败边界，与C确认私有访问，与A确认只读与占位呈现。汇总系统报告时各人分别供稿，你不事后编造他人的人工判断；AI关键纠错留实质片段，不强制堆全聊天截图。
